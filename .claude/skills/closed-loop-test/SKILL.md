# Closed-loop test

Offline metrics score predictions; the business gets the decisions. In the warehouse project the daily
labour plan promised $815 a day offline and lost $786 a day in closed loop: its capacity curve was fit
on daily averages and missed the intra-day peaks. Asking why led to a per-shift plan that saved
$3,498 a day. This test is where the best findings come from.

## Steps

1. **Decision hook.** The simulation must accept the decision as input without code changes, like the
   starter's `--staff-plan FILE.json` (`{date: {shift: n}}`). Add one for each decision a model drives
   (order quantities, routes, prices …).
2. **Train on the first two thirds of each seed's baseline run.** Produce the plan for the test days
   using only information available the evening before each day.
3. **Re-run the same seed** with the plan for the whole period (identical up to the test period, then
   the plan takes over). Compare the test days with the baseline run of the same seed.
4. **Three arms**, all on the same seeds and days:
   - today's method (the baseline run);
   - the model's plan;
   - a **no-ML policy** that uses the same insight without the model (e.g. a static crew rebalanced by
     shift). This separates what the analysis found from what the model adds.
5. **Report** in `docs/CLOSED_LOOP.md`, generated by `ml/closed_loop.py`: per arm the KPIs, the paired
   difference vs baseline with a 95 % interval, "better in k of n seeds", and the model's offline
   promise next to the simulated result.
6. **If it fails**, say so plainly in the report, then diagnose: break the KPI down by shift, hour,
   product or customer until the mechanism is visible. Fix the model, and keep the failed version and
   its numbers in the report; the story of the failure is part of the result.
7. **Safety buffers.** Try the plan with +0 %, +5 %, +10 %, +20 % on top, so the manager sees the
   service/cost curve rather than one point.
